# "Failed to upload TexturePack" (HTTP 429) at every Play: source and findings (BD-596, 2026-10-17, offline)

**CURRENT BUILD BEHAVIOR** read from `main` (`1a690653`). No Studio was used; nothing here was reproduced, so the engine-side reason is marked UNVERIFIED. Context: the [post-#392 re-walk](../2026-10-17-rewalk/README.md) (PR #422) saw about 40 `Failed to upload TexturePack (... PublishService AssetUpload failed ... HTTP 429 / Internal)` lines at the start of every Play and matched them to the 38 `SurfaceAppearance` objects under `ReplicatedStorage.Resources`.

## 1. Where the 38 come from (MEASURED, from the repo and a build)

## 2. Why Studio tries a TexturePack (UNVERIFIED)
Studio packs the maps of a `SurfaceAppearance` / `MaterialVariant` into a "TexturePack" asset through `PublishService` and logs the upload at Play. What is known here: the maps are valid cloud ids (so this is not the "local or unbound map" case), and HTTP 429 is "too many requests", which fits 38 packs (plus 4 for the variants) being queued at once. What is not known: whether the pack is tried because the place is unpublished (the re-walk place was a file, not a published place), whether the 429 is the limit or the first answer (the line also says `Internal`), or whether it is new in the current Studio build. The only DevForum thread found ([Texture Pack error](https://devforum.roblox.com/t/texture-pack-error/4752600)) has no staff answer and no confirmed cause. This was not guessed further.

## 3. Would players see it? (reasoned, not measured)
No for the log lines: the upload is a Studio-side `PublishService` call on the developer's machine; a player's client has no path to it. Whether a published place serves the same textures as the unpublished one was not measured. The game does not depend on it: `GeneTextures.apply` checks the neutral map with `ContentProvider:PreloadAsync` and, if it fails, destroys the `SurfaceAppearance` and puts the original `TextureID` back (`GeneTextureState = Unavailable`).

## 4. Fix options
| Option | Verdict |
|---|---|
| Create the `SurfaceAppearance` at runtime instead of shipping 38 templates | Not possible: `ColorMap` cannot be written from a script (the same finding is in `NpcLowPoly.luau`), which is why the templates exist |
| Drop or skip the 38 templates in the build | Not safe: all 38 are bound and used by `GeneTextures.apply` (legacy mesh dinos and eggs). It would remove the gene tint from them for a Studio-only log line |
| Skip **unbound** PBR templates in the build | Nothing to skip: no unbound or invalid map exists today. A guard is added instead (below) |
| Count the Studio lines as noise in the walk | **Done:** `tools/qa/regression_walk` no longer fails "no new errors" on a line that starts with `Failed to upload TexturePack`; the report names them (`Studio TexturePack upload lines not counted: N (BD-596)`) so they are never silent. Game errors still fail |
| Find out whether it goes away | **Studio test for the lead (no code):** Play once with `Resources.GeneSurfaces` deleted in the place (is the log clean?), once in a published place, once an hour later (is it only the rate limit?). If a published place is clean, the answer is "unpublished-place noise" and nothing more is needed |

## 5. What was changed
* `tools/verify_surface_maps.py` (new, CI): builds the place in memory and fails if any `SurfaceAppearance` / `MaterialVariant` map is not `rbxassetid://<positive id>`, or a `SurfaceAppearance` has no ColorMap; 10 mutants (empty, zero, leading zero, local file, http, no ColorMap, `null` url, no maps, MaterialVariant) must fail.
* `tools/qa/regression_walk` (`00-lib.client.luau`, `40-checkpoints.server.luau`, selftest scenario `studionoise` in `selftest/sim.luau`, `tools/verify_regression_walk.py`).
* No game code and no `resources/` file changed.
