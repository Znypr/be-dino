## 3. Interactions that were checked and held

Each item is a pair of PRs that touch the same assumption. "Held" means read against the merged source (not the PR diff) and, where a verifier exists, run.

* **`admit()` fairness (#448) and priority writes.** Priority writes (renew, settlement, load, purchases) never call `admit`. The fair path admits a player below `share / players` only while the window is under `WriteFairCeiling` 0.8 of `60 + 10 x players`, so at least 20 percent of the budget stays for priority writes (the old reserve was 40 percent). At 12 players that is 36 requests a minute against about 24 for renewals plus about 3 for settlements. Held. Empty-run settlement (#445) and the objective batch riding the renew (#444) only lower the routine volume.
* **Movement window (#449) and the pickup loops.** Server teleports go through `FallRecovery.teleport`, which calls `MovementGuard.reset`; food and crystal loops start a new window whenever a step is implausible (a teleport, a new character). A dash or leap raises `MovementSpeedLimit` and the window uses the peak over the ring plus 0.5 s. A rollback clears the guard's window and re-seeds it at the rollback point. Vertical motion is not in the window. Held; the jitter and slack numbers are still Studio work (BD-611).
* **Secret species equip (#437) and everything that reads the equipped dino.** The stored pair stays `compy`; `equippedOf` is the only reader of `equippedSecret` and is used by `progressionView`, `syncAttributes`, `equipSpecies` and `ProfileShop` (per-dino cosmetics get `ctx.equipped`). Every other reader (`Dinosaur`, `ClassMovementService`, `CombatService`, `ProgressionService`, `FeedbackService`) reads the replicated `EquippedSpeciesId` attribute, which `syncAttributes` fills from `equippedOf`. `Combat.SpeciesClasses` lists the seven secrets (penguin Water, budgiesaurus Fly). `ScaleLadder.dinoRow` serves `HitSize` and `MouthReach`. Held. The pending equip of #450 re-runs `equipSpecies`, so a secret pick is re-checked (flag, model slot, ownership) at spawn.
* **Equip next run (#450) and `already_equipped` (#445 d).** In a run, `already_equipped` clears an earlier pick and returns before any render; a valid pick answers `next_run` before `admit`, so it costs no write; `applyPending` is called from the one place that attaches a dino (`Bootstrap.server.luau` spawn). Held (F6 aside).
* **Empty-run settlement (#445) and the objective batch (#444).** The empty settlement keeps its write whenever a banked egg, a pending grant or a nest that would advance exists, and the run-end objective events are memory-only until the renew or release carries them; the settlement itself never took the objective batch. Held.
* **`ClientWorldReady` (#445 b) and StreamingEnabled (#437 era streaming).** With `StreamingEnabled` the client fires at script start, before `IslandTerrainReady`, so the server now ignores that call; `RunLifecycle.worldReady` returns true under streaming before it reads `WorldReady`, and nothing else reads the attribute. Without streaming the client waits for `IslandTerrainReady` before it fires. Held.
* **`CooldownMemory` by UserId (#445 f).** Exit cooldown (120 s retention), Fusion and Objective windows (pruned on use), Progression gap (pruned every 64 requests): all memory only, none touches a profile. Held.
* **Removed things.** No reference to `FlushSeconds`, `glideHeld`, `lastGlideRequest` or `ObjectiveConfig.FlushSeconds` remains in `src` or `tools` (the mutation tests that proved their absence pass); `ObjectiveConfig` itself is still required by `ObjectiveService` and `ObjectiveRules` and its other keys are unchanged.
* **Kanban.** BD-611, BD-613, BD-614, BD-615, BD-616, BD-618, BD-624 to BD-627 and BD-630 are Review / test, matching the code that merged; BD-612 and BD-617 are Backlog and untouched. No duplicate BD ids (`verify_doc_ids`: 504 ids).
