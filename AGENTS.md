## Game vision
Be Dino! is a Roblox dinosaur survival, growth, collection, and hatching game. In a run, a player collects food, grows, hunts/avoids predators, and eventually settles the run. The exciting payoff is watching **the eggs actually caught during that run** hatch **one at a time**, progressing from ordinary to exceptional discoveries. Runs also earn crystals and *separate bonus egg nests*. Duplicates, genetics, condition, event mutations, Shiny/BIG, collection, fusion, shops, and new playable dinosaurs give long-term progression.

The player-facing count of **catches** in the target reward loop means **the number of individual run eggs earned**, not a separate score that only unlocks 1-3 eggs or a guaranteed grant of one Base Compy per catch. Keep raw food/growth score, catch/egg count, hatched dinosaur copies, account XP, crystals, and bonus nest count distinct.

Neither rarity distribution is a committed probability table; drops should generally be common-heavy, with longer/better runs exposing more rare tiers.

- **Every earned run catch corresponds to one run egg**, stored/settled server-side. Reveal the **4 or 40 eggs sequentially (earlier 15 / 150 and 40 / 400 superseded)**, one at a time, approximately five seconds each at the current prototype speed, preferably in increasing species rarity within a batch. Do not invent additional separate immediate eggs from the old 10/100/500 catch thresholds.
- Do **not** grant direct guaranteed Base Compy copies *on top of* those eggs. A run egg can yield a random species/condition/traits when revealed; current code can also give 1-3 copies per successful egg and Cracked eggs can fail. That separate **per-egg quantity/hatch contract is a provisional prototype mechanic**, not owner confirmation that every egg must yield exactly one copy, nor permission to double-credit direct rewards.
- **Crystals** are another end-of-run reward, with map pickups as an additional source. Do not treat the example 30/220 values as an approved curve or assume the same crystal box mechanics must remain.
- **Bonus egg nests are separate from ordinary run eggs.** Nests occupy **up to five nest slots**. The long-run example offers six nests, so at most five can be claimed when all slots are empty. Show the sixth as capacity-blocked/pending rather than silently losing or covertly granting it; the final excess/expiry/claim UX is an unresolved design decision. Do not confuse this five-slot nest capacity with the currently coded five-slot ordinary egg queue.
- Score-to-egg conversion, crystal formula, exact rarity odds, per-egg 1-3 quantity, nest contents/timing, overflow, caps, and storage/UI performance for 150-egg batches all require balancing/implementation/verification. Do not report them as shipped.

## Current long-term progression decisions (2026-10-08)

**READ [advanced fusion and per-dino progression](docs/46-pattern-fusion-dino-identity-and-cosmetic-progression.md) before editing these systems.** The owner wants Base → **Gold → Emerald → Diamond**, with first Gold requiring **10 same-species/same-pattern inputs** (**2026-10-14 owner-approved ladder supersedes (and replaces 50/10/3 of 2026-10-13): Gold = 15 Base, Emerald = 4 Gold, Diamond = 2 Emerald, same species + pattern at every tier; [docs/58](docs/58-fusion-ladder-50-10-3.md), pacing in [docs/57](docs/57-fusion-ladder-options.md) section 12**). **ALL selected dinosaurs are consumed**, creating a **NEW** instance. Species and recipe-locked pattern remain; **the output's colors, condition, Shiny, BIG and event mutation are freshly rolled from ingredient-informed probabilities**. No hero's genes survive intact. The next stage and its permanent stat improvement are **guaranteed**, not random. A 2 Shiny / 10 donor example should give **10%** under a **proposed** half-weight input-proportion formula (raw 2/10 is 20%); real weights are not yet locked. A dedicated Fusion Menu must filter by same kind/pattern and traits, confirm donors and show numerical outcomes. Wheels reveal **precommitted server results** only. Blender subtle/medium material masks overlay the NEW output's DNA, never donor DNA.

A living dinosaur may **buy several auras/trails and switch between styles it owns**. Purchases are instance-bound. **None of the consumed inputs' aura/trail inventories survives fusion**; the new result starts with no paid cosmetics. Automatically protect customized/rare ingredients, display an **itemized irreversible loss warning** for any intentionally selected ones, and resolve legacy/premium purchase migration before enabling destruction. **Hatched instances retain original egg metadata**, while fused outputs retain **parent IDs/egg lineage** and newly rolled traits, not one falsely “preserved” egg. Older copies may lack provenance.

**Natural hatch probability** is for actually hatched items; **fusion outcome probability** is conditional on the selected parents and a versioned server trait-roll formula. Crafted tier contributes **earned prestige**, never a fake Gold drop percentage; bought cosmetics never contribute to rarity. **Roblox policy treats randomized combination/synthesis as potentially paid-random when inputs are Robux-linked**, so validate source eligibility and final numerical odds disclosures, enforce `PolicyService`, and keep paid release flags disabled until tested. [Roblox paid random items policy](https://create.roblox.com/docs/production/monetization/paid-random-items). **BD-058–065 are Backlog.** BD-057 Phase 1 is Review / test: a disabled, unpublished-memory-only fusion transaction ([49](docs/49-identity-fusion-phase1.md)) now with a provisional odds roller and a disabled `FusionAction` remote ([53](docs/53-bd064-fusion-server.md)); no UI or live rollout yet; shipped Build 020 behavior is unchanged. Ingredient odds, pattern-research credits and later fusion material costs are proposals, not final balance.

## How to answer and implement

1. **For "what would a 5-minute / 500-food run reward?"** use the 4-egg example above (40 was the 2026-10-13 figure, 15 the one before). Mark any invented value as an illustrative assumption. Never answer "guaranteed Compies + 1 egg + 1 nest".
2. Explicitly label **OWNER TARGET**, **CURRENT BUILD BEHAVIOR**, or **HISTORICAL TEST SPEC**. The older `N(c)=c` direct-copy allocation and 1/2/3 egg threshold appear in code and tests but are **not the owner's desired game loop**.
3. Prioritize the newer owner's explicit direction over older alpha docs, test fixtures, generated summaries, or implementation defaults. Do not rewrite history: preserve legacy specs as historical, update conflicting high-visibility references, and keep one canonical task board.
4. If asked to implement, plan a safe, server-authoritative migration: egg ownership/settlement exactly once, immutable outcome RNG, existing saves/queues, Cracked failure, five-second reveals, trait versioning, duplicate species stacks, UI scalability and reconnect/overflow behavior. Validate with tests and Studio evidence. **Never rewrite persistent profiles, enable Robux packs, or claim Studio/phone acceptance without evidence.**
5. If asked for concrete examples, show actual counts whose rarity totals sum to the egg count and identify any open economic assumptions. Ask for specific unresolved balancing decisions only if necessary for implementation; examples do not require clarification.
